## The Vision Behind Senselet

Senselet started from a simple observation: small retailers track stock in notebooks, spreadsheets and memory, and only notice a problem when a shelf is already empty. I wanted a tool that records every stock movement and uses that history to warn you before you run out.

### One Backend, Many Businesses

Senselet is multi-tenant from the first migration. Every business is an organisation, and row-level security in PostgreSQL keeps each organisation's products, sales and suppliers separate — today that is 131 policies across all 28 tables, built up through 160 migrations. Businesses can run several branches and transfer stock between them.

### Forecasting From Real Sales

Forecasts come from the inventory log, not guesswork. For each product, a Postgres function averages daily consumption over the last 30 days, estimates the days until stockout, and adds a 7-day safety buffer. When stock runs low, an edge function sends an alert to the business's Telegram chat.

### An Agent That Can Actually Do the Work

The part I am proudest of is the assistant: a Gemini function-calling agent with 33 tools. It can check and adjust stock, transfer between branches, propose purchase orders and reconcile invoices, and each role (admin, manager, clerk) only sees the tools it is allowed to use. If one model fails, requests fall through to other Gemini models and then to OpenRouter.

### The Solo Developer Challenge

Building Senselet alone meant owning every layer: the React and Vite frontend, 21 TypeScript edge functions, the database, billing through Chapa and the Telegram bot. It also meant I had to be my own QA team, so the platform now has 266 automated tests, and I stress-tested the offline sync queue against a deliberately failing network until it stopped losing or duplicating writes.
