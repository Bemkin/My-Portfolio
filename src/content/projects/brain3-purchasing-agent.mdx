### How it works

A stock check runs whenever its endpoint is called, either from the dashboard's run button or by a scheduler that sends the shared secret.

```
┌──────────────────┐     ┌───────────────────────┐     ┌──────────────────────┐
│ Trigger          │ ──▶ │ /api/cron/check-stock │ ──▶ │ Google Gemini        │
│ dashboard button │     │ stock <= reorder pt,  │     │ one batched JSON     │
│ or secret call   │     │ grouped by supplier   │     │ request              │
└──────────────────┘     └───────────────────────┘     └──────────┬───────────┘
                                                                  │
                                                                  ▼
┌──────────────────┐     ┌───────────────────────┐     ┌──────────────────────┐
│ Resend email     │ ◀── │ Purchase order per    │ ◀── │ Zod validation or    │
│ (Auto-Pilot or   │     │ supplier + line items │     │ fallback formula     │
│ after approval)  │     │ + audit log entries   │     │                      │
└──────────────────┘     └───────────────────────┘     └──────────────────────┘
```

### 1. Finding low stock

- The check loads every active item with its supplier and keeps the ones where current stock is at or below the reorder point.
- Low-stock items are logged in one batch insert and grouped by supplier.

### 2. Asking Gemini

- All low-stock items go to Gemini in a single `generateContent` call with `temperature: 0` and a JSON response type, while the audit log entry and the PO count are fetched in parallel.
- The system prompt sets hard rules: never order more than the spare capacity, only use suppliers from the list, assume 1 unit a day when sales are 0, cover at least 1.5 times the lead-time demand, and set urgency by days to stockout.

### 3. Validating, or falling back

- The response is parsed, matched to each supplier and checked against `BatchReorderResponseSchema` with Zod. Each recommended quantity is then capped at max capacity minus current stock.
- If the call fails, the JSON cannot be parsed, validation fails or a supplier is missing from the answer, that supplier's order uses a fixed formula instead:

```
reorder quantity = min(reorder_point × 2 − current_stock, max_capacity − current_stock)
                   (at least 1 unit)
```

- Fallback orders are marked as such on the PO and in the audit log.

### 4. Purchase orders and email

- Supplier orders are built in parallel with `Promise.allSettled`, so one failing supplier does not stop the others. PO numbers come from the existing count plus the supplier's position, to avoid clashes within a run.
- In **Auto-Pilot** mode each PO is created as approved and emailed to the supplier through Resend, then marked as sent.
- In **Approval** mode POs wait as pending; approving one in the Purchase Orders page sends the email.

### 5. Dashboard

- Pages for inventory, purchase orders, suppliers, settings and the audit log, with a Ctrl/Cmd+F search shortcut and a stock-alert drawer.
- A simulator drops stock on 3 to 6 random items, or resets it, to demo the flow end to end. Inventory can be exported to CSV.

### Engineering notes

- **Auditability:** every check, AI request, fallback, PO, approval and email failure is written to an `ai_audit_logs` table with severity and source, and each run logs its duration.
- **Data model:** six PostgreSQL tables in Supabase with 17 indexes, including a partial index on stock versus reorder point for active items, plus a seed script.
- **Validation:** Zod schemas guard every write route (POs, suppliers, settings, email, simulation) as well as the AI output.
- **Server-side keys:** the Supabase service-role key is only used in a server-side client inside API routes.
- **Performance:** the dashboard caches API responses in memory for 30 seconds and refreshes them in the background.
